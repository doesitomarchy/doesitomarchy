Open API

Everything on this site is open data. Read the catalog and the test results as JSON, or, if you write a test tool, send diagnostic reports straight in.

Reading

No key needed. Every read endpoint returns JSON, allows any origin (CORS), and may be cached for a minute. Catalog data is CC BY-SA 4.0: credit DoesItOmarchy and share alike.

  • GET /api/v1: an index of the endpoints.
  • GET /api/v1/macs: every Intel Mac, with its verdict range and configuration IDs.
  • GET /api/v1/macs/{identifier}: one Mac (e.g. MacBookPro11,3) and all its configurations.
  • GET /api/v1/configs/{id}: one configuration: components with hardware IDs, its port layout (connectors, with the criteria each connector is tested for, and portmap_url, the port map drawing as an SVG, when there is one), the criteria that apply, the current status of each, and its latest reports.
  • GET /api/v1/capabilities: the test criteria, including retired ones.
  • GET /api/v1/schema: the diagnostic report format, as JSON Schema.
  • GET /api/v1/reports/{code}: where a report stands: pending, accepted, rejected (with the reason) or retracted.
  • POST /api/v1/match: send a hardware probe (product_name, board_id, cpu, pci, usb), get the Mac and, in config, its configuration, or null when several fit equally. best lists every configuration tied at the top (one when it's exact; their order within a tie means nothing). candidates ranks them all, with the IDs each matched and the parts not reported. It's the same matching as Identify my Mac.
curl -s {{.Base}}/api/v1/macs/MacBookPro11,3
curl -s -X POST {{.Base}}/api/v1/match \
  -d '{"product_name":"MacBookPro8,2","pci":["1002:6760"]}'

Becoming a source

A source is a test tool that submits reports. Each one has an ID and a key. To get one, open an issue with your tool's name, homepage and what it tests. A maintainer registers it and sends you the key privately.

  • Keys look like doi_ followed by 32 characters. We keep only a hash, so a lost key is replaced, not recovered.
  • Keep the key in your tool's build or server, not in a public repository. If it leaks, ask for a new one; the old one stops working at once.
  • Each source may submit up to {{.PerHour}} reports an hour.

Submitting a report

Send one report per test run, as JSON or YAML, with your key:

curl -s -X POST {{.Base}}/api/v1/reports \
  -H "Authorization: Bearer $DOI_KEY" \
  -H "Content-Type: application/json" \
  --data-binary @report.json

You don't need to know the configuration ID. Send the model identifier and the hardware probe, and the server finds the configuration. Include the CPU name (hardware.cpu): it tells apart configurations that share every device. If the probe still fits several, the report is taken anyway, and a maintainer picks the right one.

A new report is pending until a maintainer reviews it. The reply:

201 Created
{"code": "3f9a1c07be", "state": "pending",
 "config": "macbookpro8-2-15-early-2011-a", "candidates": [],
 "flags": [], "status_url": "{{.Base}}/api/v1/reports/3f9a1c07be"}

Errors come back as {"error": "…", "problems": ["…"]}:

  • 400: the report isn't valid. problems lists every issue, not just the first.
  • 401: no key or an unknown key. 403: the key was revoked, or the report names a different source.
  • 413: over 1 MiB. 415: a format we don't read.
  • 422: no configuration in the catalog fits this hardware.
  • 429: the hourly limit; wait for Retry-After seconds.

The report format

Format doesitomarchy/report/v1, fully described by the schema. Items use the criteria IDs from /api/v1/capabilities; leave out anything you didn't test. Each result says how it was tested: automatic (the tool checked), observed (the tester looked) or fixture (with test equipment, such as a loopback plug).

{{.Example}}
  • tested_at is when the test ran, with a time zone. The site shows every time in UTC.
  • Port criteria can be reported per connector: ports.usb-a@left-2, using the connector IDs in the configuration's layout. Connectors are named by side and numbered left to right as you face that side. A criterion counts as fully verified only when every connector it applies to has passed.
  • Don't send serial numbers, network addresses, or user and computer names. They're removed anyway, but it's better never to send them.
  • Put the check's output in evidence when something fails or only partly works. It's what helps someone fix it.

The notice testers must see

Before your tool submits, it must show the tester this notice (or a faithful translation) and let them stop. Submitting counts as agreeing. Send the text you showed in consent_notice.

Ground rules

  • Only send results from real test runs on real hardware.
  • Maintainers review every report and can reject or retract it, with a reason that's shown on the site.
  • The format may gain optional fields. A breaking change would get a new version (/v2), and v1 would keep working.
